I keep running into two kinds of documentation, and one of them never gets read.

The first kind explains the code. It sits next to the function and says what the parameters mean. Useful sometimes, and it goes stale the moment someone refactors without reading it.

The second kind explains the situation. Why this exists. What we tried first and why it failed. What will break if you change this. Who to ask. That one gets read all the time, because it answers the question you have at the moment you have it.

I write the second kind now and I'm ruthless about the first. If the function name and the types already say it, a comment repeating it is noise that will rot.

I put the second kind in a file at the top of the directory called decisions. Not a wiki. A file. Wikis drift away from the code. A file gets renamed in the same commit that changes the thing, or it gets noticed in review. Nobody reads a wiki. Everybody reads the file sitting next to the code they're editing.
