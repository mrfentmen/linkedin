A retry loop I added to handle flaky networks nearly took down a service by hammering it.

I thought the logic was careful. If the call fails, wait a bit and try again. Three attempts. What I hadn't thought about is that a failing server is the worst possible moment to send more requests, and everyone retrying at once makes the failure worse.

The fix isn't to retry harder. It's to retry less and agree on a rule. Wait longer each time, so the fourth attempt is minutes later not milliseconds. Add a random offset so a thousand clients don't fire together. That second one is the part I'd never have guessed. Randomness makes the retries spread out instead of arriving in a wave.

Then there's the question underneath all of it. Should this retry at all. If the call isn't safe to repeat, retrying might charge a card twice. Retries need to know that.

Mine didn't. It was one line and it could have duplicated work. I got away with it because the operation happened to be harmless. I got lucky and I've stopped pretending that's the same as being right.

I made one endpoint safe to call twice and it changed how confident I felt about the whole system.

It was a create action. Call it once and you get one thing. Call it again with the same request and you got a second copy. A user who tapped twice because the first tap looked slow ended up with two of everything.

That one change removed a whole class of problem. Retries became safe. A flaky connection stopped being able to duplicate work. What it buys is the ability to retry anything without checking whether it's safe first, and that's worth much more than the code.

I stored a job in memory and lost it when the process restarted, which took me a while to notice because I never restarted it.

The design was simple. A queue in the process, a worker taking items off it. Fine on a laptop that stays on. Not fine anywhere else.

I learned that a process isn't permanent. It crashes, it gets redeployed, the machine reboots. Everything in memory goes with it, silently, and nobody gets an error. So the queue has to live somewhere that outlives the process. A table is enough. Pick a row, mark it as taken, delete it when done.

The bit I missed the first time is what happens if the worker dies halfway. The row stays marked forever and that job never runs again. So the mark needs a timestamp and a rule that reclaims anything older than a few minutes.

That's the whole outbox pattern. Store it first, then work. Anything still only in memory is not queued. It is a hope. I lost maybe four jobs before I noticed. Silent data loss is the worst kind because there's nothing to read.

Two machines disagreed about what time it was by four seconds and it broke a signature check.

The check was correct. Sign with the current time, verify that the time is recent. Simple and standard. My server and the other one had drifted by a few seconds, so a signed request looked like it came from the future.

Nothing was hacked. Two clocks just disagreed, which is normal and expected. The fix is to allow a window. A couple of minutes either side instead of a few seconds. That absorbs normal drift without accepting an old request.

What I learned is that time is a distributed resource and I had been treating it like a local one. I treat every machine as having its own opinion. So now anything involving clocks gets an explicit tolerance, written as a named number in the config, not buried in the code. If it's a security boundary the value matters and someone should have to think about it.

I expected an exotic bug. The cause was ordinary.

I tried to load a large file into memory and my program died with no warning and no error message.

But I was loading all of it, then making a copy, then a third copy while filtering. Three times the size of the file in memory at peak.

Since then the default is streaming unless there's a reason not to, and the reason has to be written down. Loading everything is the convenient choice and convenience has a ceiling.
