The backup ran every night and reported success for about two years, and that report only ever meant the copy completed, which is not the same thing as the copy being usable. It never meant anybody could read it. The archive format had changed twice in that window.

One old snapshot saved us. It was on a machine somebody forgot to decommission. We got the data from July and rebuilt the delta by hand, and I spent the weekend not sleeping well.

We restore to a scratch machine every month now. It's scheduled, it has an owner, and the job fails loudly if the restore doesn't open. That's forty minutes of compute a month. Cheapest insurance we have.

A backup you have never restored is a belief system. It's comfortable and it isn't a copy of anything.

Everybody should have that page. You don't need it until you suddenly do, and by then the systems you'd have looked in are gone.

I did a code review last month that took four minutes and changed what we shipped. Four minutes. I almost skipped it.

I evaluate a model by the same test every time, and the test is a task I've already failed with the previous one. That's it.

Benchmarks are useful for a first filter and useless for a decision. What I want to know is whether the specific thing that broke last month breaks again this month, and the only way to know is to run it.

I keep a small set of tasks for this. Ten tasks. All drawn from real work. All with a known answer. I've run the same ten against five models this year. The scores moved in a way the leaderboards didn't predict.

I don't upgrade on launch day. That gap is why. A model that wins on a reasoning suite can still fail my task, and my task is the only one that pays.

So I'll keep the ten tasks and I'll add one every time something breaks. Over time that list becomes the most valuable thing I own.

A bug appeared every Tuesday afternoon for four months and the cause was a cron job nobody owned. I want to write down how we found it, because the method is the point.

We couldn't reproduce it. We tried for two weeks and failed, which is the normal outcome when the trigger is time. So we stopped trying to reproduce and started trying to record. Every time it happened we wrote three lines. What the user did, what time it was, what the system said.

After five occurrences the Tuesday pattern was obvious and nobody had seen it, because the reports were spread across a chat and a ticket and two emails. Then it was a thirty minute fix. A cleanup task ran on Tuesdays and deleted rows a report was still reading.

The lesson isn't about cron. It's that the four month cost came from the recording, not the fixing. We had five pieces of evidence and nowhere to put them. If you can't reproduce a bug, stop trying. Start a file. Make the next occurrence write itself down.

I read the source of a library for the first time in three years and found out I'd been using it wrong. Not badly. Just wrong, in a way the docs allowed.

The function had a default that made it look like it waited. It didn't wait. It returned immediately and the thing I thought was a callback was a timeout handler, so half my calls were racing and I'd been blaming the network. The docs weren't wrong. They were thin.

That's the trade with dependencies. The docs describe intent and the source describes behaviour. When those two differ, the source is the truth and the source is always available. I try to open the source of any package I put on a hot path. Not read all of it. Read the function I call and the one it calls.

Three minutes of reading has saved me two outages this year. The docs were fine both times and I was still wrong.
